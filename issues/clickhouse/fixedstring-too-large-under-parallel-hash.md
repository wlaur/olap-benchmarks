# `TOO_LARGE_STRING_SIZE` deserializing `FixedString` under a `parallel_hash` join

**Status: draft, not filed.** Do the checks in [Before filing](#before-filing) first. Last
observed on ClickHouse 26.7.1.1315; not re-verified since.

## Summary

TPC-H Q5 against the official ClickHouse TPC-H schema fails with

```
Code: 131. DB::Exception: Too large sizes of FixedString to deserialize: 1152761100:
While executing DelayedJoinedBlocksTransform. (TOO_LARGE_STRING_SIZE)
```

The reported size varies run to run (`1152761100`, `1196753150`, …) and is nowhere near the
declared `FixedString(25)`, which suggests a length is being read from the wrong offset rather than
a genuinely oversized value.

The strongest signal: **the first execution succeeds and the second fails**, with identical SQL, no
writes in between, and no other client connected. That points at parallel-join state or a cache
rather than at the data.

| | |
| --- | --- |
| Reproduces on | `26.6.1.1193` and `26.7.1.1315` (latest stable at time of writing) |
| Image | `clickhouse:<version>-jammy` |

| Dataset | TPC-H SF10 generated by [tpchgen-rs](https://github.com/clflushopt/tpchgen-rs) |
| Schema | verbatim from `tests/benchmarks/tpc-h/init.sql` (`n_name FixedString(25)`, etc.) |

## Reproduction

Load TPC-H SF10 using `tests/benchmarks/tpc-h/init.sql`, then run TPC-H Q5 **twice** on the same
connection:

```sql
SELECT n_name, sum(l_extendedprice * (1 - l_discount)) AS revenue
FROM customer, orders, lineitem, supplier, nation, region
WHERE c_custkey = o_custkey AND l_orderkey = o_orderkey AND l_suppkey = s_suppkey
  AND c_nationkey = s_nationkey AND s_nationkey = n_nationkey AND n_regionkey = r_regionkey
  AND r_name = 'ASIA' AND o_orderdate >= DATE '1994-01-01' AND o_orderdate < DATE '1995-01-01'
GROUP BY n_name
ORDER BY revenue DESC;
```

Observed:

```
iteration 1: OK, 5 rows
iteration 2: Code: 131 ... Too large sizes of FixedString to deserialize: 1196753150
```

## Bisect

`join_algorithm` is the deciding factor. The default is `direct,parallel_hash,hash`, so
`parallel_hash` is selected and the query fails.

| `join_algorithm` | result |
| --- | --- |
| default (`direct,parallel_hash,hash`) | fails on the 2nd execution |
| `parallel_hash` | fails on the 1st execution |
| `hash` | 3 consecutive executions OK |

Setting `query_plan_use_new_logical_join_step = 0` does **not** help, so it does not appear to be
specific to the new logical join step.

## Possibly a second issue: session left locked

After the failure the HTTP session stays unusable and every subsequent query on it returns

```
Code: 373. DB::Exception: Session <uuid> is locked by a concurrent client. (SESSION_IS_LOCKED)
```

despite there being no concurrent client. In our benchmark one failing query therefore took out 17
of 22 subsequent ones. Recovery required discarding the client and opening a new session. If this
is not expected after a query-level exception, it is worth reporting separately — it turns one bad
query into a dead session.

## Before filing

1. **Search existing issues** for `TOO_LARGE_STRING_SIZE`, `Too large sizes of FixedString to
   deserialize`, and `DelayedJoinedBlocksTransform`. The varying bogus length is a distinctive
   signature and may already be tracked.
2. **Minimise.** TPC-H SF10 is a poor reproducer to attach. The ingredients appear to be: a
   `FixedString(N)` column carried through a multi-way join, executed with `parallel_hash`, at
   enough scale to spill across blocks. Try synthesising two tables with `generateRandom` over a
   join key plus a `FixedString(25)` payload and joining them, rather than shipping the dataset.
   File with the synthetic case if it reproduces, and mention TPC-H Q5 as the original context.
3. Confirm on `x86_64` too — everything above is ARM64, and a platform-specific note would help.
